## 정답 및 해설

**Q1. B.** 마스터만 발급(`TryValidate`의 AddPotion, 검증 통과 후 `PotionInstanceIds.Next()`). A는 ID 0 포션이 되고(생성자 `PotionInstance(data, keyword)`), C/D는 클라이언트마다 ID가 달라지거나 겹친다. 다른 클라이언트는 마스터가 정해 준 ID를 그대로 쓴다.

**Q2. B.** `RpcApply`에서 `Ignored`/`VersionGap`/`Inconsistent`일 때 내 요청이면 `Complete(Fail(OutOfSync))`로 바로 끝내고, `Ignored`가 아니면 `RequestResync()`로 전체 목록을 요청한다(1초 쿨다운). 결과를 알 수 없으니 호출 쪽은 `State`를 확인해야 한다.

**Q3. C.** `TryValidate`는 사본(재료, 포션, 시체 상자)과 `Version`을 바꾸지 않는다. 다만 `PotionInstanceIds.Next()`, `_nextCorpseId++`로 발급 번호는 소비한다(Apply 도착 전에 다음 요청이 검증돼도 같은 번호가 나가지 않게). 적용이 실패하면 번호만 건너뛴다. `Version`은 `Apply`에서만 오른다. (TryValidate 안의 `apply.Version = Version + 1`은 복사본 값일 뿐이다.)

**Q4. B.** 개인 인벤토리는 순수 로컬(소유자만), 10칸 기본(`DefaultCapacity`), 재료/포션 아무 칸. 255는 시체 상자 칸 수 한계(`MaxCorpseSlots`, byte 1개로 전송).

**Q5.** `Timeout`, `NotInRoom`, `OutOfSync`. (`Invalid`, `Full` 등은 마스터가 `RpcDenied`로 보낸다.)

**Q6.** 늦게 들어온 쪽 `RpcReady`(`OnJoinedRoom` 또는 `Start`의 `SendReady`) -> 마스터 -> `RpcSnapshot`(그 사람에게만) -> `TryLoadSnapshot`. (마스터 자신은 `RpcReady`를 무시 `info.Sender.IsLocal`.)

**Q7.** `Ignored`: `apply.Version <= Version` (이미 적용한 오래된 메시지). `VersionGap`: `apply.Version != Version + 1` 이면서 그보다 큰 경우(중간 메시지를 놓침). 이상 두 검사 후에야 내용을 적용한다.

**Q8.** `Leftover`는 시체 상자에 못 들어간 만큼이므로, 요청한 쪽이 자기 개인 인벤토리에 되돌려야 한다(안 하면 아이템 소실). 거부(`Blocked` 등)된 경우에는 아무것도 놓이지 않았으니 전부 되돌린다.

**Q9.** `Slots == null`, 길이 0, 길이 > 255(`MaxCorpseSlots`), 아이템이 하나도 없음(`HasAnyItem`), `AreSlotsValid` 실패(재료: ID<=0 / 개수<=0 / 모르는 재료 / 한 칸 한도 초과, 포션: null 또는 InstanceId<=0). 깨진 메시지는 `TryUnpackRequest` 실패 -> `TryPeekRequestId`로 즉시 `Invalid` 거부.

**Q10.** `personal.AddPotion` -> 경고 로그 후 `-1` (ID<=0은 버려짐, 칸에 안 들어감). `Potions.Add` -> 경고 후 `false`. ID 0 포션은 `InventoryPacker.TryReadPotion`에서도 거부되므로 시체 상자/스냅샷을 못 탄다. 올바른 방법: `AddPotionAsync` -> `Outcome.Potion`(마스터가 ID 부여) -> `personal.AddPotion`.

**Q11.** `AreSlotsValid`에서 `slot.Count > InventoryRules.GetMaterialLimit(...)`(99 < 150)로 false -> `Invalid` 거부, 시체 상자 안 만들어짐, `CorpseId` 번호도 소비되지 않음(검증 실패라 `_nextCorpseId++` 전에 반환). 같은 취지로 `PreviewPlace`도 빈 칸에 놓을 때 한 칸 한도를 적용한다(`PutCorpseSlot`). 호출한 쪽은 `Invalid`면 확실한 실패이므로 `personal.Load(slots)`로 복구할 수 있다.

**Q12.** B의 `Apply`는 `apply.Version(7) != Version(5)+1` -> `VersionGap`. B는 요청자이므로(`IsLocalActor`) 즉시 `Fail(OutOfSync)`로 끝나고 `RequestResync`(쿨다운 1초)로 `SendReady` -> 마스터가 스냅샷 전송 -> B가 `TryLoadSnapshot`으로 사본을 통째로 교체(`OnReloaded`). (이전 동작은 코드로 확인하지 않았으나, 즉시 완료가 없으면 제한 시간 5초 뒤 `Timeout`이 되는 구조다.) 마스터에서는 이미 성공했을 수 있으므로 `OutOfSync`는 "사본을 확인하라"는 신호다.

**Q13.** 마스터만 직접 사본을 바꾸면 마스터는 "검증 즉시 변경", 나머지는 "메시지 수신 후 변경"으로 경로가 둘이 되어 순서/버전/예외 처리가 달라지고 어긋날 틈이 생긴다. 전원이 같은 `Apply` 경로(버전 검사 포함)를 쓰면 코드가 하나라 사본이 같은 순서로 같은 값을 가지며, 마스터도 같은 코드로 시험되고 오프라인 모드에서도 동일하게 동작한다. 또 `TryValidate`를 내용 불변으로 둘 수 있어서 "검증은 판정, 변경은 Apply"로 책임이 분리된다.

**Q14.** 위치는 사람마다 다를 수 있다. 다른 사람의 Apply가 먼저 도착해 목록이 바뀌었거나, 스냅샷 직후 순서가 달라졌다면 같은 index가 다른 포션을 가리킨다(엉뚱한 포션이 빠짐). ID는 마스터가 부여한 불변의 이름이라 요청이 도착하는 사이 목록이 바뀌어도 같은 포션을 가리키고, 이미 없다면 `NotFound`로 안전하게 거부된다. 동시에 두 명이 같은 포션을 요청하면 먼저 도착한 한 명만 성공한다.
