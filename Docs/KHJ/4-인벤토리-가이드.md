# 인벤토리 시스템 가이드

> 위치: `Assets/KHJ/Script/Inventory/**` (네트워크는 `Network/`). 네임스페이스 `Enzeun.Runtime`.

## 한 줄 요약
팀 공유 재료/포션/시체 상자는 **"요청(RequestId) → 마스터 검증 → 전원 적용(사본 버전 번호)"** 으로 동기화하고, 개인 인벤토리(10칸)는 **내 클라이언트에만** 있는 순수 로컬 칸 배열이다.

## 구조 한눈에

| 층 | 클래스 | 역할 |
|---|---|---|
| 규칙 (순수 C#, Photon 모름) | `MaterialInventory` | 팀 재료. 재료 ID별 개수 + 종류별 한도. 칸 없음 |
| | `PotionInventory` | 팀 포션. `PotionInstance` 개별 보관(스택 안 함), 100개 한도 |
| | `PersonalInventory` | 개인 10칸. 칸마다 재료 묶음 또는 포션 1개. 시체 상자 내용물도 같은 클래스 |
| | `InventorySlot` (struct) | 한 칸. `Kind`(Empty/Material/Potion) + 재료(ID, Count) 또는 `Potion` |
| | `CorpseBox` | 시체 상자 데이터(ID, 위치, `Slots`=PersonalInventory) |
| | `InventoryRules` | 재료 한도 `GetMaterialLimit` (음수/조회 실패 -> 99, 0 -> 보관 불가) |
| | `PotionInstanceIds` | 포션 인스턴스 ID 발급 (`Next`, `Reset`) |
| | `TeamInventoryState` | 위 셋을 묶은 "사본". `TryValidate`(마스터) / `Apply`(전원) / 스냅샷 |
| | `InventoryCommand`, `InventoryMessages`, `InventoryPacker` | 명령 구조체, 메시지 byte 변환, ID만 담은 byte 묶음 |
| 네트워크 (Photon) | `InventoryNetworkSyncManager` | RPC 송수신 + `*Async` 대기. 규칙은 전혀 모르고 `TeamInventoryState`에 위임 |

**왜 나눴나**: 규칙이 Photon을 모르니 에디터에서 "마스터 1 + 클라이언트 2"를 흉내 내어 시험할 수 있다. 매니저는 메시지 배달만 한다.

## 핵심 규칙과 이유
- **요청 -> 마스터 검증 -> 전원 적용**: 동시에 두 명이 같은 포션을 꺼내려 해도 마스터가 도착 순서로 한 명만 통과시킨다. 권한을 한 곳에 두면 충돌 해결이 공짜다.
- **마스터도 Apply 메시지를 받아서 바꾼다**: `TryValidate`는 사본을 바꾸지 않는다. 마스터가 직접 바꾸면 마스터만 다른 경로를 타서 어긋날 틈이 생기므로, 전원이 똑같은 `Apply` 경로를 쓴다.
- **사본 버전**: `Apply`마다 +1. `apply.Version <= Version`이면 `Ignored`, `!= Version+1`이면 `VersionGap`(메시지를 놓침), 내용이 맞지 않으면 `Inconsistent`.
- **재동기화**: `VersionGap`/`Inconsistent`/깨진 Apply -> `RequestResync` -> `RpcReady`(마스터에게 "스냅샷 줘"). 최소 간격 `ResyncCooldownSeconds`(1초)로 요청 폭주 방지. 마스터는 어긋날 수 없으므로 보내지 않는다.
- **늦게 들어온 사람**: `OnJoinedRoom`(또는 이미 방에 있으면 `Start`)에서 `SendReady` -> 마스터가 `RpcSnapshot`을 그 사람에게만 보냄 -> `TryLoadSnapshot`(끝까지 읽어 문제없을 때만 교체, 실패하면 기존 사본 유지).
- **포션 인스턴스 ID는 마스터만 발급** (`TryValidate`의 AddPotion에서 `PotionInstanceIds.Next()`). 두 클라이언트가 각자 발급하면 ID가 겹친다. ID가 없는(<=0) 포션은 `PersonalInventory.AddPotion`, `PotionInventory.Add`가 거부하고, byte를 풀 때 `TryReadPotion`도 ID<=0이면 거부한다.
- **`TryValidate`는 내용은 안 바꾸지만 번호는 소비한다** (포션 ID, 시체 ID). Apply 도착 전에 다음 요청이 검증돼도 같은 번호가 나가지 않게 하려는 것. 적용이 실패하면 번호만 건너뛴다.
- **마스터 교체 미지원**: 발급 번호가 마스터 메모리(static)에만 있어 새 마스터가 1부터 다시 발급하면 ID가 겹친다. 마스터 이탈 = 방폭 전제 (NetworkFlowManager 쪽에서 처리). (시체 ID는 스냅샷에 `_nextCorpseId`가 담기지만 포션 ID 번호는 담기지 않는다.)
- **꺼내기는 index가 아니라 ID** (`TakePotion(instanceId)`): 사람마다 목록 순서가 어긋날 수 있고, 요청이 도착하는 사이 목록이 바뀐다. ID는 바뀌지 않는다.
- **시체 상자 검증**: `CreateCorpse`는 칸 수 1~255, 아이템 1개 이상, `AreSlotsValid`(재료=알려진 ID + 한 칸 한도 이하, 포션=InstanceId>0)를 통과해야 한다. 클라이언트가 보낸 값은 믿지 않는다.
- **`PreviewPlace`가 빈 칸에도 한 칸 한도를 적용**: 한도를 넘는 묶음이 시체 상자에 들어가는 우회로를 막는다. 마스터는 `PreviewPlace`로 "얼마 들어가나"를 계산(`Slot`/`Leftover`)하고, 전원은 그 결과를 그대로 적용한다.
- **개인 인벤토리는 동기화 안 함**: 소유자만 쓰므로 동기화 비용이 낭비. 죽을 때 `TakeAll`(먼저 비우고 돌려줌 -> 아이템이 두 곳에 존재하지 않음, 복제 방지) -> `CreateCorpseAsync`.
- **오프라인 모드**: 내가 마스터라서 같은 코드가 그대로 돈다. (단 `PhotonNetwork.InRoom`이 true여야 한다.)
- **패킹**: SO는 못 보내므로 ID만 보낸다. 모든 묶음 맨 앞에 버전 1 byte, 남는 byte가 있으면 실패. 풀기 실패는 예외 없이 `false`.

## 네트워크 흐름

```
[요청자]                         [마스터]                          [전원 (마스터 포함)]
 *Async(...) 호출
  RequestId 발급, _pending 등록
  RpcRequest ───────────────────>  TryUnpackRequest (깨짐 -> TryPeekRequestId로 즉시 Invalid 거부)
  (제한 시간 5초 타이머 시작)       TryValidate  (내용 불변, ID 번호만 소비)
                                    ├ 거부 ─> RpcDenied (요청자에게만) ─> Complete(Fail(reason))
                                    └ 통과 ─> RpcApply (RpcTarget.All) ──────────────>  TryUnpackApply
                                                                                         state.Apply(Version+1 확인)
                                                                                          ├ Applied    -> 요청자면 Complete(Ok(outcome))
                                                                                          ├ Ignored    -> 내 요청이면 Fail(OutOfSync)
                                                                                          └ VersionGap / Inconsistent
                                                                                             -> 내 요청이면 Fail(OutOfSync) + RequestResync(쿨다운 1초)
[어긋난 사람 / 늦게 들어온 사람]
 SendReady = RpcReady ─────────>  CreateSnapshot ─> RpcSnapshot (그 사람에게만) ─> TryLoadSnapshot ─> OnReloaded
```
- 시간 초과: `_pending`에서 제거하고 `Fail(Timeout)`. 이후 늦게 온 Apply는 사본에는 반영되지만 이 요청에는 전달되지 않는다. **Timeout이어도 실제로는 성공했을 수 있다** -> 사본(`State`)을 확인할 것.
- 마스터가 자기 요청을 보내면 RPC가 호출 안에서 바로 처리되어 결과가 이미 채워져 있을 수 있다(오프라인 포함).

## 팀원이 쓰는 법 (`InventoryNetworkSyncManager.Instance`)

모든 `*Async`는 `UniTask<InventoryResult>` (`Success`, `Reason`, `Outcome`). 방에 없으면 `NotInRoom`, 5초(`_requestTimeoutSeconds`) 내 무응답이면 `Timeout`.

| 메서드 | 인자 | 성공 시 `Outcome` | 실패 이유(Reason) |
|---|---|---|---|
| `AddMaterialAsync` | materialId, count | `Value` = 실제로 넣은 개수(한도 초과분은 잘림) | Invalid(모르는 ID, <=0), Full(0개 들어감) |
| `RemoveMaterialAsync` | materialId, count | `Value` = 뺀 개수 | Invalid, NotEnough(일부만 빼지 않음) |
| `AddPotionAsync` | `PotionInstance crafted` | `Potion` = **마스터가 ID를 부여한** 포션 | Invalid(null/Data null/모르는 포션·키워드), Full(100개) |
| `TakePotionAsync` | instanceId | `Potion` = 꺼낸 포션 | NotFound(동시 요청 시 늦은 쪽) |
| `CreateCorpseAsync` | position, `InventorySlot[]` (TakeAll 결과) | `CorpseId` | Invalid(빈 배열, 아이템 0개, 255칸 초과, 한도 초과/ID 없는 포션) |
| `TakeCorpseSlotAsync` | corpseId, slotIndex | `Slot` = 꺼낸 내용 (받은 쪽이 개인 인벤에 넣어야 함) | NotFound, SlotEmpty |
| `PutCorpseSlotAsync` | corpseId, slotIndex, content | `Slot` = 놓인 내용, `Leftover` = 못 놓은 내용(되돌려 받아야 함) | NotFound, Blocked(거부 시 전부 되돌릴 것) |

공통 실패: `Timeout`, `NotInRoom`, **`OutOfSync`** (내 요청의 Apply가 `Ignored`/`VersionGap`/`Inconsistent`라 결과를 알 수 없음. 전체 목록을 다시 받는 중이니 `State`를 확인).
읽기/이벤트: `State.Materials.Counts/GetCount/OnChanged`, `State.Potions.Items/Count/OnChanged`, `State.Corpses`, `State.OnCorpseCreated/OnCorpseChanged/OnReloaded`. **`Add`/`Remove`/`SetCount`를 직접 부르면 사본이 어긋난다** (읽기 전용으로만).

### 개인 인벤토리 (`PersonalInventory`, 기본 10칸, 로컬 전용)

| 메서드 | 동작 | 반환 |
|---|---|---|
| `AddMaterial(id, count)` | 같은 재료 칸 먼저 채우고 빈 칸 사용. 한 칸 한도는 재료 SO | 못 넣고 남은 개수 (0이면 전부) |
| `AddPotion(potion)` | 첫 빈 칸. null/ID<=0이면 경고 후 버림 | 칸 index, 실패 -1 |
| `Move(from, to)` | 빈 칸=이동, 같은 재료=한도까지 합침, 그 외=교환 | 바뀌었으면 true |
| `TryPlace(index, content, out leftover)` | 빈 칸/같은 재료 칸에만 놓음(교환 없음) | 하나라도 놓았으면 true |
| `PreviewPlace(...)` | TryPlace의 계산만 (마스터 검증용) | 놓을 수 있으면 true |
| `TakeSlot(index)` | 칸 통째로 꺼내고 비움 | 꺼낸 `InventorySlot` (빈 칸/범위 밖이면 default) |
| `TakeAll()` | 전부 칸 위치 그대로 꺼내고 비움 | `InventorySlot[]` |
| `Load(source)` | 기존 내용 지우고 불러옴, 모든 칸에 이벤트 | - |
| `GetMaterialCount(id)` | 여러 칸 합산 | int |
| 이벤트 `OnSlotChanged(int index)` | 칸이 바뀔 때 | |

## 호출 예시

```csharp
// 1) 제작 -> 팀 포션 -> 내 개인 인벤토리
var net = InventoryNetworkSyncManager.Instance;
InventoryResult r = await net.AddPotionAsync(crafted);      // crafted 는 ID 없는 새 포션
if (!r.Success) { Debug.LogWarning($"포션 등록 실패 : {r.Reason}"); return; }   // 재료 환불 등은 호출 쪽 책임
int idx = personal.AddPotion(r.Outcome.Potion);              // 반드시 Outcome.Potion (ID 부여된 것)
if (idx < 0) { /* 개인 칸이 가득 참. 팀 포션에는 이미 들어가 있음 -> 팀에 그대로 둔다 */ }

// 2) 죽음 -> 시체 상자. 실패하면 슬롯을 지니고 있다가 되돌린다
InventorySlot[] slots = personal.TakeAll();                  // 먼저 비워서 복제 방지
InventoryResult c = await net.CreateCorpseAsync(transform.position, slots);
if (!c.Success)
{
    if (c.Reason == InventoryDenyReason.Timeout || c.Reason == InventoryDenyReason.OutOfSync)
        { /* 실제로는 만들어졌을 수 있음: State.Corpses 확인 후 판단, 재시도는 중복 위험 */ }
    else
        personal.Load(slots);                                // Invalid/NotInRoom 등 확실한 실패 -> 그대로 복구
}
```

## 하지 말아야 할 것
- 클라이언트에서 `new PotionInstance(data, keyword)`로 만든 포션(ID 0)을 개인/팀 인벤토리에 직접 넣기 -> 버려진다. 반드시 `AddPotionAsync`의 `Outcome.Potion`을 쓴다.
- `PotionInstanceIds.Next()`를 마스터 검증 밖에서 호출하기 (ID 중복).
- `State.Materials.Add` 등 규칙 클래스를 직접 호출해 팀 사본 수정하기 (본인 사본만 어긋남).
- 포션을 index로 꺼내는 요청 만들기 (`TakeAt`은 로컬 목록용). 꺼내기는 `TakePotionAsync(instanceId)`.
- `Outcome.Leftover`/`Slot` 무시하기 (아이템 소실). 성공 후 개인 인벤토리에 넣는 것은 호출 쪽 몫.
- `Timeout`을 곧 "실패"로 단정하고 재시도하기 (중복 생성/중복 차감 위험).
- 마스터 교체/이탈을 계속 진행하는 것으로 가정하기 (방폭 전제).
- 게임 내 정신력을 "지능"으로 쓰기 (용어는 "정신력").

## 아직 연결 안 된 것
- 이 폴더 밖에서 인벤토리 클래스를 쓰는 코드가 없다 (UI, 제작창, 사망 처리, 월드 오브젝트 드롭 등이 `*Async`/`PersonalInventory`를 부르는 곳은 아직 없음). `WorldObjectNetworkSyncManager`는 주석 언급 정도.
- 시체 상자의 화면 오브젝트는 `OnCorpseCreated`를 보고 만드는 쪽의 몫(미구현). 개인 인벤토리 저장/불러오기도 없음.
- 마스터 교체 시 포션 ID 번호 이어받기 (스냅샷에 포션 `_next` 없음, 방폭 전제).
- 스냅샷 수신 시 대기 중이던 내 요청은 즉시 끝나지 않고 타임아웃/개별 완료를 따른다.
- **설계 구멍**: `TakePotionAsync`로 팀 포션을 꺼낸 뒤 개인 인벤토리가 가득 차 `AddPotion`이 -1 이면, 꺼낸 포션을 되돌릴 경로가 없어 사라진다. 꺼내기 전에 개인 인벤토리에 빈 칸이 있는지 먼저 확인할 것. (되돌리기 방식은 미정)
- Play 모드 실동작(2인 이상 실제 룸)은 이 문서 작성 시 확인하지 않았다. 코드 기준으로만 검증.

## 용어집
- **사본(Copy)**: 모든 클라이언트가 가진 `TeamInventoryState`. **사본 버전**: Apply마다 1씩 오르는 번호.
- **요청(Request)/적용(Apply)/거부(Deny)**: 클라 -> 마스터 / 마스터 -> 전원 / 마스터 -> 요청자.
- **RequestId**: 요청자가 붙이는 번호. 결과와 짝짓는 용도. **RequesterActor**: 요청자의 ActorNumber.
- **스냅샷(Snapshot)**: 전체 상태를 묶은 byte. 늦게 들어온 사람/어긋난 사람에게 마스터가 보냄.
- **InstanceId / CorpseId**: 마스터가 발급하는 포션 개체 번호 / 시체 상자 번호.
- **Outcome**: 성공한 요청이 돌려주는 값(개수, 포션, 칸, 남은 칸, 시체 ID).
- **방폭**: 마스터가 나가면 방을 닫는 처리.
- **정신력**: 게임 내 수치 이름 ("지능"이라고 쓰지 않는다).
